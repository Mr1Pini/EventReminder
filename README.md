# EventReminder

Веб-додаток для планування подій: календар і список, створення, редагування та видалення подій, фільтр за важливістю, пошук, персональний доступ через авторизацію. Кожен користувач бачить лише власні події.

Проєкт зроблено як тестове завдання (junior fullstack, React/Node).

## Можливості

**За технічним завданням**

- Реєстрація та вхід: email і пароль **та** Google OAuth; сесії на JWT.
- Події з назвою, датою й часом, описом і важливістю («звичайна», «важлива», «критична»).
- Створення (зокрема кліком по даті в календарі), редагування, видалення з підтвердженням.
- Перегляд у вигляді календаря та списку.
- Фільтр за важливістю, пошук за ключовими словами.
- Збереження подій у PostgreSQL; доступ лише до власних подій.

**Додатково**

- Позначка «виконано» та фільтр статусу «Усі / Активні / Виконані»; маркер «Прострочено».
- Календар у режимах рік, місяць, тиждень, день; на вузьких екранах стартує режим «День».
- Список із вкладками «Майбутні / Минулі», групуванням за днями та пагінацією (10 подій на сторінку).
- Стан інтерфейсу в URL: вигляд, фільтри, пошук, вкладка й сторінка зберігаються при оновленні та в посиланнях.
- Темна тема з перемикачем «Світла / Темна / Системна» (без «спалаху» при завантаженні).
- Адаптивна верстка (перевірено на 375, 768 і 1280 px), доступність: підписи, фокус, клавіатурна навігація, контраст не нижче WCAG AA.
- Український інтерфейс через next-intl; усі тексти в одному файлі `src/messages/uk.json`.

## Стек

Next.js (App Router) + TypeScript + Tailwind CSS + Prisma + PostgreSQL. Логіка роботи з БД — у Server Actions (файли з `"use server"`); папка `src/app/api` містить лише маршрут next-auth.

## Розгортання з нуля

1. **Клонуйте репозиторій і встановіть залежності**

   ```bash
   git clone <адреса-репозиторію>
   cd EventReminder
   npm install
   ```

2. **Створіть порожню базу даних**

   ```bash
   psql -U postgres -c "CREATE DATABASE eventreminder;"
   ```

   Використайте окрему БД саме для цього проєкту: міграція створює таблиці `users`, `accounts`, `events`.

3. **Створіть файл `.env`** на основі шаблону й заповніть його (опис змінних нижче)

   ```bash
   cp .env.example .env        # PowerShell: Copy-Item .env.example .env
   ```

4. **Згенеруйте клієнт Prisma, застосуйте міграцію й наповніть БД тестовими даними**

   ```bash
   npm run db:generate
   npm run db:migrate
   npm run db:seed
   ```

   Команди `db:*` читають `.env`, тому файл має існувати до їх запуску. Клієнт генерується в `src/generated/prisma` (папка в `.gitignore`), тож `db:generate` потрібен після кожного клонування.

5. **Запустіть застосунок**

   ```bash
   npm run dev
   ```

   Відкрийте <http://localhost:3000> і увійдіть із демо-доступом (див. нижче).

Для production-збірки: `npm run build`, потім `npm start`. Для розгортання за межами `localhost` перегляньте налаштування адреси сайту в документації Auth.js (змінні `AUTH_URL` / `AUTH_TRUST_HOST`).

### Змінні оточення

| Змінна | Обов'язкова | Опис |
|---|---|---|
| `DATABASE_URL` | так | Рядок підключення до PostgreSQL, наприклад `postgresql://USER:PASSWORD@localhost:5432/eventreminder` |
| `AUTH_SECRET` | так | Випадковий секрет для підпису сесій. Згенерувати: `node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"` |
| `AUTH_GOOGLE_ID` | ні | Client ID для входу через Google |
| `AUTH_GOOGLE_SECRET` | ні | Client secret для входу через Google |

Файл `.env` не потрапляє в Git; у репозиторії лежить лише `.env.example` без секретів.

## Вхід через Google (необов'язково)

Без `AUTH_GOOGLE_ID` і `AUTH_GOOGLE_SECRET` кнопка Google не показується, а вхід за email і паролем працює повністю.

1. Відкрийте [Google Cloud Console](https://console.cloud.google.com/) і створіть проєкт (або виберіть наявний).
2. **APIs & Services → OAuth consent screen**: налаштуйте екран згоди (тип External, назва застосунку, ваш email).
3. **APIs & Services → Credentials → Create credentials → OAuth client ID**, тип **Web application**.
4. У полі **Authorized JavaScript origins** додайте `http://localhost:3000`.
5. У полі **Authorized redirect URIs** додайте `http://localhost:3000/api/auth/callback/google`.
6. Скопіюйте Client ID і Client secret у `.env` як `AUTH_GOOGLE_ID` та `AUTH_GOOGLE_SECRET`.
7. Перезапустіть `npm run dev`.

Для розгорнутого сайту додайте в обидва поля адресу свого домену. Поки застосунок в режимі Testing, у Google Cloud Console треба додати свій акаунт до тестових користувачів.

Автоматичного об'єднання акаунтів немає: якщо email уже зареєстровано паролем, вхід через Google з тією самою адресою покаже повідомлення про інший спосіб входу.

│  ├─ components/ui/          # універсальні UI-компоненти без бізнес-логіки
│  ├─ hooks/                  # спільні React-хуки

│  ├─ i18n/                   # конфіг next-intl
│  ├─ messages/               # переклади (uk.json)
│  └─ types/                  # розширення типів next-auth

## Ключові архітектурні рішення

- **Feature-папки.** Усе, що стосується однієї області (серверні функції, схеми, константи, типи, компоненти), лежить разом.
- **Server Actions замість REST.** Читання (`queries.ts`) і зміни (`actions.ts`) — це файли `"use server"`, що експортують лише async-функції. Папка `api` використовується тільки для next-auth.
- **Договір результату.** Очікувані помилки (валідація, «не знайдено», «email зайнятий») повертаються як `{ success: false, errorKey }`, а не кидаються винятками. Клієнт показує переклад за ключем.
- **Безпека на кожному запиті.** Кожна серверна функція перевіряє сесію, валідує дані через zod і додає `userId` до умови запиту (`where: { id, userId }`). `userId` береться із сесії, а не з параметрів; `passwordHash` ніколи не залишає сервер.
- **Сесії JWT.** next-auth зберігає сесію в cookie без таблиці сесій; у БД лише `users` і `accounts`. Доступ до сторінок перевіряється в layout-ах груп маршрутів, без middleware.
- **Стан в URL.** Вигляд, фільтри, пошук, вкладка й сторінка живуть у `searchParams`: посилання відтворює той самий стан, дані читає Server Component.
- **Дати в UTC.** У БД час зберігається як `timestamptz` (UTC), показується в часовому поясі браузера. Форматування й групування днів відбувається лише на клієнті, а календар вантажиться з `ssr: false`, щоб не було розбіжностей під час гідратації. Усі утиліти дат — у `src/lib/date.ts`.
- **Дизайн-токени.** Кольори задані CSS-змінними в `globals.css` і підключені до Tailwind через `@theme`; компоненти використовують лише токени. Темна тема лише переозначає значення токенів, календар FullCalendar отримує ту саму палітру.
- **Типізовані переклади.** Ключі `uk.json` перевіряються TypeScript; тип `ErrorKey` виводиться з файлу перекладів.

## Відомі обмеження та можливі покращення

**Обмеження**

- Календар завантажує всі події користувача за фільтрами, без обмеження діапазону дат: достатньо для демонстраційного обсягу, але не для тисяч подій.
- Немає автоматичних тестів: якість забезпечують строгий TypeScript, ESLint, перевірка збірки й ручні сценарії.
- Немає rate limiting і підтвердження email.
- Реєстрація розкриває, що email уже зайнятий.
- Акаунти (пароль / Google) автоматично не зливаються: це свідоме рішення задля безпеки.
- `next-auth` v5 і FullCalendar v7 — нові мажорні версії; API може змінюватися.
- У dev-режимі вимкнено логування аргументів Server Functions (`logging.serverFunctions` у `next.config.ts`), щоб паролі не потрапляли в термінал.

**Можливі покращення (поза межами проєкту)**

- Підтвердження email і скидання пароля поштою.
- Rate limiting для входу та реєстрації.
- Повторювані події та перетягування подій у календарі.
- Нагадування про події на пошту.
- Завантаження подій у календарі за видимим діапазоном дат.
- Адмін-панель.
